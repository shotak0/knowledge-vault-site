# 公理的設計：機能要求の独立を保つ

## 1. 概要

公理的設計（Axiomatic Design）は、Nam P. Suh が提唱した設計理論であり、「良い設計とは何か」を2つの公理で判定する枠組みである。設計を「何を達成するか（機能要求 FR）」から「どう達成するか（設計パラメータ DP）」への写像として捉え、FR 同士の独立が保たれているか（独立公理）と、設計の情報量が小さいか（情報公理）で評価する。

この知識で中心になるのは独立公理である。FR と DP の対応を設計行列に書くと、設計の結合の状態が形として現れる。対角行列なら非結合（uncoupled）で理想、三角行列なら分離可能（decoupled）で、DP を決める順序を守れば成立する。それ以外の形は結合（coupled）であり、一つの変更が他の機能へ波及する設計である。「結合度が高い」という曖昧な評価を、行列の形という目に見える判定に変える点が、この理論の実用的な核である。

もともとは機械・製造系の設計理論であり、対象は製品やプロセスが中心である。ソフトウェアなど非物理の対象への適用には注意が要る。その論点は出典の内容ではないため、6節で AI による考察として分けて記す。

## 2. 基本概念

- **FR（Functional Requirement、機能要求）**：設計が達成すべき「何を」を表す変数。機能領域に属する。FR は解法（どうやって）を含まない形で書くのが原則であり、FR の集合は設計の目的を過不足なく表す最小の集合であることが求められる。
- **DP（Design Parameter、設計パラメータ）**：FR を満たすために選ぶ「どうやって」を表す変数。実体（物理）領域に属する。部品、構造、寸法、方式などが DP になる。
- **4つのドメイン（領域）**：設計は、顧客ドメイン（顧客のニーズ）、機能ドメイン（FR）、物理ドメイン（DP）、プロセスドメイン（プロセス変数 PV）の4領域で捉えられる。設計とは、左の領域が提示する課題に対して、右の領域が解を返す写像を、領域をまたいで繰り返す行為である。
- **設計方程式・設計行列**：FR と DP の関係は {FR} = [A]{DP} と書ける。[A] が設計行列で、成分 Aij は「DPj が FRi に影響するか」を表す。
- **独立公理（Axiom 1）**：FR の独立を保つこと。各 DP を調整しても、対応する FR 以外に影響しないことが理想であり、少なくとも FR と DP の数が一致し、影響の及ぶ先が制御できる形であることが求められる。
- **情報公理（Axiom 2）**：独立公理を満たす設計の中では、情報量の小さいものが良い設計である。情報量は、設計範囲（許容範囲）とシステム範囲（実現可能な範囲）の共通範囲から I = log（システム範囲／共通範囲）と測る。共通範囲が大きいほど情報量は小さい。
- **系（corollary）**：2公理から導かれる実務的な指針。代表的なものに、系1「干渉設計の独立化」、系2「FR の最小化」、系6「設計許容範囲の最大化」がある。

## 3. 詳細解説

### 設計は写像である

公理的設計の出発点は、設計を「課題から解への写像」と見ることである。顧客のニーズは、そのままでは設計できない。まず機能ドメインで「何を達成するか」を FR として言い直し、次に物理ドメインで「どう達成するか」を DP として選ぶ。さらに DP を実現するプロセスをプロセスドメインで決める。左のドメインが「何を」を、右のドメインが「どうやって」を担当するという分業が、すべての判定の土台になる。FR に解法が紛れ込むと、この分業が崩れ、後の判定ができなくなる。

### 独立公理と設計行列の3分類

FR と DP の対応を設計行列に書くと、結合の状態は次の3種類に分類できる（行列の形による分類は公理的設計の標準的な整理であり、本 Knowledge の参照元である講義資料・邦訳書に基づく）。

| 分類 | 行列の形 | 意味 |
| --- | --- | --- |
| 非結合（uncoupled） | 対角行列 | 各 DP が対応する FR にだけ影響する。理想形 |
| 分離可能（decoupled） | 三角行列 | 影響が一方向にだけ及ぶ。DP を決める順序を守れば、各 FR を順に満たせる |
| 結合（coupled） | それ以外の形 | 影響が循環する。一つの DP を変えると他の FR が動き、調整が iteration（反復）になる |

たとえば2つの FR と2つの DP では、対角は「DP1→FR1、DP2→FR2」の一対一対応であり、三角は「DP1 が FR1 と FR2 の両方に効くが、DP2 は FR2 にだけ効く」形である。三角の場合、先に DP1 を決めてから DP2 を決めれば衝突しない。つまり decoupled な設計は「決める順序」という運用条件つきで成立する設計であり、順序の情報も設計の一部になる。対角にできないことを即座に失敗とみなすのではなく、三角に持ち込めるか、という一段弱い判定を用意している点が、この理論の現実的なところである。

### 情報公理と許容範囲

独立公理を満たす候補が複数あるとき、情報公理が選択の基準になる。情報量は「設計が狙いどおりに収まる確実さ」の逆数的な量であり、設計範囲とシステム範囲の共通範囲が広いほど小さい。実務的な帰結は系6「設計許容範囲の最大化」である。許容範囲を必要以上に狭くすると共通範囲が痩せ、情報量が増え、わずかなばらつきで失敗する設計になる。職人技に頼る設計が公理に反するとされるのは、許容範囲の小ささ（再現の難しさ）が情報量として表れるためである。

### 失敗パターン

公理的設計では、設計の失敗は次の形で整理できる。

- **DP 不足 → 干渉（coupled）**：FR の数に対して DP が足りないと、一つの DP が複数の FR を兼ねることになり、干渉する。FR と DP の数を一致させる、という独立公理の要請に反する。
- **DP 過多 → 冗長**：DP が多すぎると、同じ FR に複数の DP が重なって効き、調整の自由度が衝突する冗長設計になる。
- **許容範囲が小さすぎる → 情報量の増大**：作れる範囲より狭い設計範囲を指定すると共通範囲が小さくなり、情報公理に反する。考慮すべき変数が増え、設計が複雑化する。

### 系の代表例

- **系1：干渉設計の独立化** — 結合している部分は、DP の選び直しや追加で独立化を試みる。
- **系2：FR の最小化** — FR は必要最小限に絞る。FR が増えるほど、独立を保つことは難しくなる。
- **系6：設計許容範囲の最大化** — FR を設定するときは、許容範囲を可能な限り大きく取る。
- その他の系には、部品の統合、標準の利用、対称性の利用、情報量の小さい独立設計などがある。

## 4. 仕組み・構造

```mermaid
flowchart LR
    CA[顧客ドメイン<br/>ニーズ] --> FR[機能ドメイン<br/>FR：何を達成するか]
    FR -->|設計行列 A で対応づけ| DP[物理ドメイン<br/>DP：どう達成するか]
    DP --> PV[プロセスドメイン<br/>PV：どう作るか]
```

設計行列の読み方の手順は次のとおりである。

1. FR を、解法を含まない形で、最小の集合として書き出す。
2. 各 FR に対応する DP を選ぶ。FR と DP の数を一致させる。
3. 「DPj を変えると FRi が変わるか」を判定し、設計行列に印を付ける。
4. 行列の形を分類する。対角なら uncoupled、行や列の並べ替えで三角にできるなら decoupled、それ以外は coupled。
5. coupled な部分があれば、DP の選び直し、DP の追加、FR の分割・統合で独立化を試みる（系1）。decoupled の場合は、DP を決める順序を明記する。
6. 候補が複数残れば、情報公理で比較する。許容範囲と共通範囲を見て、情報量の小さい方を選ぶ（系6）。

## 5. メリット・デメリット

メリットは、設計の良し悪しに、好みではなく公理という共通の物差しを持ち込めることである。「結合している」という指摘が、行列の形という検証可能な形で示せるため、議論が感覚論になりにくい。FR と DP を分けて書く discipline（規律）自体も、仕様の曖昧さを早期に露出させる。また、失敗が「DP 不足」「DP 過多」「許容範囲過小」に分類できるため、直し方の方向も定まりやすい。

デメリットは、FR の書き出しに設計者の判断が大きく入り、同じ対象でも FR の切り方で結論が変わりうることである。公理は判定の基準を与えるが、FR と DP の候補を生み出す創造の部分は助けない。また、もともと製造系の設計を念頭に置いた理論であり、要求が動的に変わる対象や、物理パラメータに落としにくい対象では、情報量のような定量評価がそのままでは使いにくい。

## 6. 活用例

出典（Source）に記録された活用の文脈は、製造系の製品・プロセス設計である。許容範囲と熱処理プロセスの範囲から情報量を計算する例（ブリネル硬さの例）のように、物理量と製造能力が数値で与えられる対象で、2公理はそのまま判定に使える。タグチメソッド（主要な DP の決定）や TRIZ（FR と制約を満たす DP の提案）は、公理と接続する道具として位置づけられている。

### AIによる考察：ソフトウェアへ当てはめる場合の注意

以下は AI による考察であり、出典の記事の内容ではない。公理的設計をソフトウェアの診断に使う発想は存在するが、次の限界を踏まえて使うべきである。

- **FR 抽出の主観性**：コードベースから FR をどう切り出すかで設計行列の形は変わる。機能を粗く切れば対角に近づき、細かく切れば結合が増える。したがって、行列の形は対象そのものの性質だけでなく、切り方への依存を含む。LLM に FR 抽出と行列作成を任せる方法は、結合の当たりを付ける手早い物差しにはなっても、客観的な測定にはならない。
- **DP の対応物の曖昧さ**：ソフトウェアでは DP にあたるものがモジュール、クラス、関数、設定など複数層あり、どの層を行列の列にするかで結論が変わる。共有ライブラリのように、意図的に多くの機能へ効く部品もあり、「1つの DP が複数の FR に効く」ことが常に悪とは限らない。
- **コードの依存を直接見るなら DSM が本命**：コードの結合を機械的に測るなら、要素同士の依存を行列に書く DSM（Design Structure Matrix）の方が対象に近い。import や呼び出しのグラフから行列を自動生成でき、循環依存も直接現れる。公理的設計の行列が「FR と DP という異なるドメイン同士の対応」であるのに対し、DSM は「要素と要素の依存そのもの」を扱う。両者は競合ではなく、公理的設計は「あるべき対応の判定」、DSM は「現状の依存の記録」に強い、という使い分けが妥当である。

要するに、ソフトウェアに対して公理的設計は、診断の自動測定器としてではなく、「FR と DP を分けて考える」「決める順序を意識する」「循環する影響を嫌う」という設計の見方の枠組みとして使うのが適切である。
