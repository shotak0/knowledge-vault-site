# ハーネスの定義と流派

## 1. 概要

ハーネスエンジニアリングとは、AIエージェントが同じ失敗を繰り返さないよう、モデルの外側（環境）を設計することである。ただし「ハーネス」という言葉の指す範囲は論者によって異なり、代表的な定義が5つの流派に整理できる。流派ごとに、ハーネスとコンテキストの包含関係の向きまで逆になる対立があった。

2026年に入ると、構成要素の整理や形式の標準化が進み、流派間の言葉づかいは数か月でほぼ一つに収束したとされる。この知識は、木下雄一朗のスライド「ハーネス設計入門」の第1部をもとに、定義の地図を再利用可能な形に整理したものである。日付や動向は同資料の記述に基づく。

## 2. 基本概念

- **ハーネス（Harness）**：モデルの外側にある環境・仕組みの設計対象である。もとの意味は馬具で、エージェントの進路を制御するものの比喩として使われる。
- **ハーネスエンジニアリング**：エージェントが同じ失敗を繰り返さないよう、モデルの外側を設計する営みである。
- **コンテキスト**：モデルに渡される文脈情報である。ハーネスとの包含関係が流派によって逆になる。
- **コンテキスト設計（コンテキストエンジニアリング）**：モデルに渡す文脈を設計することである。Fowler派ではハーネスはこの特殊形とされる。
- **語彙の収束**：論者ごとに異なっていた用語や構成要素の理解が、時間とともに揃っていく過程である。
- **Agent Plugins**：Skills と MCP サーバーを1つのフォルダ形式にまとめる標準形式である。プラグイン形式の標準化の現在地として資料に登場する。

## 3. 詳細解説

### 5つの流派

同じ「ハーネス」でも、論者が手本にした実装によって意味の範囲が違う。資料では次の5派に整理される。

| 流派 | 代表者 | 中核主張 |
| --- | --- | --- |
| Chase派 | Harrison Chase（LangChain） | モデル以外のすべてがハーネス |
| Hashimoto派 | Mitchell Hashimoto | 失敗したら環境を再設計せよ |
| Fowler派 | Birgitta Böckeler（Thoughtworks） | コンテキスト設計の特殊形として定義する |
| Chawla派 | Avi Chawla（教育系） | LLM の OS 層である |
| Codex派 | Ryan Lopopolo（OpenAI Codex） | 三重の入れ子であり、スケールで壊れる問題への答えである |

Chase派は最も広い定義で、モデルでないものは全部ハーネスに含める。Hashimoto派は、定義の広さよりも「失敗のたびに環境側を直す」という運用哲学に重心がある。Fowler派は、ハーネスをコンテキスト設計の中に位置づける。Chawla派は、モデルをアプリケーションにたとえればハーネスは OS 層にあたる、という比喩で捉える。Codex派は、入れ子構造と、規模が大きくなったときに壊れる問題への対処として捉える。

### 包含関係の対立

流派の対立が最もはっきり出るのは、「ハーネスとコンテキストのどちらが外側か」である。

- Chase派と Chawla派では、ハーネス ⊃ コンテキスト（ハーネスが外側で、コンテキストはその一部）である。
- Fowler派では、コンテキスト ⊃ ハーネス（コンテキスト設計が外側で、ハーネスはその特殊形）となり、向きが逆になる。

同じ言葉を使っていても前提の図が違うため、議論がかみ合わないことが起きる。ハーネスの議論を読むときは、まずその論者がどちらの図を前提にしているかを確認する必要がある。

### 語彙の収束と標準化（2026年）

資料によれば、2026年3〜7月にかけて収束が進んだ。主な出来事は次のとおりである（いずれも資料の記述に基づく）。

- 2026-03-10：LangChain が「The Anatomy of an Agent Harness」でハーネスの構成要素を整理した。
- 2026-04-19：Addy Osmani が「ハーネスはモデル同士より互いに似てきている」と述べた。
- 2026年6月：Build 2026 で Agent Harness の安定版が出て、Pydantic v2.0 がハーネス中心に再設計された。
- 2026年：Linux Foundation が Agentic AI Foundation を設立した（MCP、AGENTS.md、Goose が関係する）。
- 2026-08-06：Agent Plugins 1.0 が示された。Skills と MCP サーバーを1つのフォルダ形式（plugin.json、skills/、mcp.json）にまとめるもので、Vercel の発案で、Amazon、Cursor、GitHub、Microsoft、OpenAI が策定し、Google も参加した。対応実装は ChatGPT、Codex、Cursor、GitHub Copilot、Kiro、VS Code である。

一方で、互換性はまだ一部にとどまる。Claude Code は独自形式のままで未対応であり、Skills か MCP の片方だけ対応のクライアントもある。hooks、コマンド、rules は標準化の対象外で、クライアントごとに異なる。言葉はまとまり、形式の標準化も始まったが、移植性が完全に確保されたわけではない。

### 実証について

資料では、モデルを変えずにハーネスだけで成績や品質が変わった実証として3つの例（ベンチマークの順位、設定による差、品質低下に関するもの）が示される。ただし図表中心のスライドであり、具体的な内容はトランスクリプトからは確認できない。この知識では、実証例が提示されているという事実のみを扱い、個別の数値は扱わない。

## 4. 仕組み・構造

定義の対立と収束は、次のように整理できる。

- **対立の軸**：ハーネスの範囲（モデル以外のすべてか、コンテキスト設計の一部か）と、包含関係の向き（ハーネス ⊃ コンテキストか、その逆か）である。
- **収束の進み方**：まず構成要素の整理（Anatomy のような分類）が共有され、次に言葉づかいが揃い、最後に形式（プラグイン形式など）の標準化が始まる。言葉の収束が形式の標準化に先行する。
- **残る差異**：標準化の対象は Skills と MCP が中心で、hooks、コマンド、rules はクライアントごとの実装に残る。したがって「標準化された」と言っても、環境全体の移植性とは一致しない。

## 5. メリット・デメリット

メリット：

- 定義の地図を持つことで、ハーネスに関する記事や議論を読むときに、論者の前提（流派）を判別できる。
- 包含関係の対立を知っていれば、用語のすれ違いによる議論の空転を避けられる。
- 標準化の現在地（何が揃い、何がまだバラバラか）を押さえると、ツール選定や移植の判断材料になる。

デメリット：

- 定義の整理そのものは実務の設計を直接は進めない。地図に時間をかけすぎると、環境の改善が遅れる。
- 収束や標準化の記述は時点依存であり、新しい資料や実装の変化で前提が古くなる。
- 流派の分類は資料の著者による整理であり、論者本人の自己分類とは限らない。

## 6. 活用例

- ハーネスに関する新しい記事を読むときに、著者が Chase派的な広い定義で話しているのか、Fowler派的にコンテキスト設計の一部として話しているのかを見分ける。
- チーム内で「ハーネス」という言葉を使うときに、包含関係の図を先に共有し、用語の前提をそろえる。
- Skills や MCP サーバーを複数クライアントで使う計画を立てるときに、Agent Plugins のような標準形式と、各クライアントの対応状況を確認する。
- 定義を押さえたうえで、実際の設計（馬具と柵の使い分け）に進む。設計の具体は [ハーネスとガードレールの設計](harness-and-guardrail-design.md) を参照すること。
