# ルールは地図ではなく罠：新規ルールの3条件と索引型の構成

## 1. 概要

AI コーディングエージェントに常時読み込まれるルールファイルには、コードを読めば分かる構造の説明（地図）ではなく、慣れていても踏んでしまう罠だけを書く、という原則である。Zed のルールファイル（.rules）の考え方をもとに整理した。

地図を書かない理由は二つある。ルールファイルはすべてのセッションで毎回読み込まれるため、価値の低い1行は毎回のコンテキストを無駄にすること。そして地図（モジュール構成やデータの流れ）はすぐに古くなり、エージェントはコードを読めば自分で把握できることである。

この原則と対になる運用として、新しいルールの追加には3条件すべてを満たすことが求められ、追加の採否はエージェントではなく人間がレビューで決める。また、関連する構成として、Sentry の「ルートの指示ファイルは短い索引に徹し、詳細は領域ごとのファイルとスキルに分ける」形もあわせて整理する。

## 2. 基本概念

- **地図**：モジュール構成やデータの流れといった、コードの構造の説明。コードを読めば把握でき、すぐに古くなるため、ルールファイルには書かない。
- **罠**：慣れた人でも踏んでしまう、コードを読むだけでは気づけない注意点。ルールファイルに書くのはこちらだけである。
- **新規ルールの3条件**：新しいルールが満たすべき条件。慣れた人でも間違える、繰り返し起きる、行動に移せるほど具体的、の3つすべてである。
- **ルールの追加提案**：エージェントが作業中にルールファイル（.rules）を直接編集せず、PR の説明に提案として出し、人間がレビューで採否を決める運用。
- **索引型の構成**：ルートの指示ファイルを全体の概要と「どこを読むか」の案内だけに絞り、詳細は領域ごとの指示ファイルとスキルに置く構成（Sentry の形）。

## 3. 詳細解説

### なぜ地図を書かないのか

ルールファイルは、すべてのセッションで毎回読み込まれる。つまり、書いた行は一度きりではなく、セッションのたびにコンテキストを占有し続ける。価値の低い1行は、毎回の無駄になる。

さらに、地図の内容（モジュール構成やデータの流れ）は、コードが変わればすぐに古くなる。古くなった地図は、無いよりも誤解を招く。一方で、エージェントはコードを読めば構造を自分で把握できる。だから地図は、書く理由が薄い。

逆に罠は、コードを読んでも気づけない。慣れた人でも踏むような注意点は、コードの外から渡すしかない。ルールファイルの役割は、この「外から渡すしかないもの」に絞る、というのが原則である。

### 新規ルールの3条件

Zed の .rules では、新しいルールには次の3条件をすべて満たすことが求められている。既存ルールの編集や明確化は、いつでも歓迎されている。

1. **慣れた人でも間違える**：コードベースに慣れた人でも、そのルールがなければ間違えること（非自明であること）。
2. **繰り返し起きる**：一度ではなく、複数回起きたこと。一つのセッションで複数回起きた場合も数える。
3. **行動に移せるほど具体的**：漠然とした原則ではなく、具体的な指示であること。

実際の罠の例として、失敗しうる処理の結果を捨てないというルールが、書き換え例つきで示されている。条件を満たすルールは、このように「何をどう書くか」まで具体的に言える、というのが3条件目の意味である。

### 採否は人間が決める

何を罠とするかは、AI に決めさせない。Zed では、エージェントは作業中に .rules を直接編集できない。代わりに、PR の説明にルールの追加提案として出し、採否は人間がレビューで決める。

これは、ルールファイルの肥大化を防ぐ仕組みでもある。エージェントが自分の判断でルールを足し続けると、ファイルは太り、毎回のコンテキストの無駄が増える。足す判断を人間のレビューに通すことで、3条件の審査が実際に行われる形になっている。

### 索引型の構成（Sentry）

書く量を減らすもう一つの形が、Sentry の索引型の構成である。

- ルートの AGENTS.md は、全体の概要、コマンドの注意、作業場所ごとにどのファイルを読むかの案内でほぼ終わる。公開されているスキルの定めでは、60行未満を目標とし、100行は決して超えない。
- 領域ごとの作法は、その領域の AGENTS.md に置く（バックエンド、テスト、フロントエンドなど）。
- 作業の手順はスキルに置く（Sentry では29本）。
- CLAUDE.md の中身は、AGENTS.md を参照する1行だけにし、二重管理を避ける。

常に読ませるのは短い索引だけで、詳細はコードの近くに置き、どれを開くかは AI が決める。Zed の罠の原則が「何を書くか」の基準だとすれば、Sentry の索引型は「どこに書くか」の構成である。

## 4. 仕組み・構造

ルールを置く場所の判断として整理すると、次のようになる。

| 書きたいこと | 置き場所 |
| --- | --- |
| コードを読めば分かる構造 | 書かない（地図は書かない） |
| 慣れていても踏む罠で、3条件を満たす | ルールファイル（人間がレビューで採否） |
| 領域ごとの作法 | その領域の指示ファイル |
| 作業の手順 | スキル |
| 全体の概要と、どこを読むかの案内 | ルートの指示ファイル（索引） |

## 5. メリット・デメリット

メリット：

- ルールファイルが短く保たれ、毎回のコンテキストの無駄が減る。
- 3条件が、新しいルールを足すかどうかの審査基準としてそのまま使える。一度だけ起きたことや、漠然とした原則を足さずに済む。
- 採否を人間のレビューに通すため、エージェントの自己判断でルールが増え続けることがない。

デメリット・注意点：

- 「罠かどうか」の判断には、そのコードベースへの慣れが必要で、基準の運用自体に人の手間がかかる。
- 地図を書かない前提は、AI がコードを読んで構造をつかめることに信頼を置いている。コードの規模や状態によっては、索引や最小限の案内が要る場合がある（Sentry 型の索引がその補いになる）。
- 3条件は Zed の実践であり、すべてのプロジェクトにそのままの形で合うとは限らない。

## 6. 活用例

- **ルール追加のレビュー基準**：自分のリポジトリで AGENTS.md に行を足すとき、「慣れた人でも間違えるか」「繰り返し起きたか」「行動に移せるほど具体的か」の3つで審査する。一度しか起きていないことは、まず様子を見る。
- **エージェントへの運用の組み込み**：エージェントにルールファイルを直接編集させず、作業の報告に「ルール追加の提案」を出させ、人が採否を決める形にする。
- **肥大化した指示ファイルの整理**：ルートのファイルが長くなっていたら、地図にあたる記述を削り、領域の作法は領域のファイルへ、手順はスキルへ移し、ルートを索引に寄せる。
