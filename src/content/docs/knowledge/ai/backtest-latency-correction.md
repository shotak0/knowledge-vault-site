# バックテストにおけるレイテンシ補正

## 1. 概要

過去データで取引モデルを検証するバックテストにおいて、購入したヒストリカルデータと実稼働環境との差（レイテンシ）を補正する知識である。出典は HFT（高頻度取引）の文脈で、Tardis や Databento から購入できるヒストリカルデータには、bot が実際に受信するデータに含まれるレイテンシがないため、そのままバックテストに使うと実際のトレードとの状況の差が大きくなる、という問題を扱う。

対処は、実機で短期間のリアルタイムデータを実測し、同じ期間のヒストリカルデータと比較して遅延をパラメータ化し、そのパラメータをヒストリカルデータに適用してからバックテストすることである。対象とする遅延は、マーケットデータの受信遅延、発注遅延、イベント受信までの遅延の3種類で、さらに遅延のばらつき（jitter）まで含めると、遅延の変動に強いシステムを検証できる。

## 2. 基本概念

- **バックテスト**：過去の市場データを使って、取引モデルの有効性を検証すること。
- **ヒストリカルデータ**：過去の市場データを記録したもの。Tardis や Databento などで長期間分を購入できる。記録上の時刻で整っており、実稼働で生じる受信の遅れは含まれない。
- **実稼働データ（リアルタイムデータ）**：bot が本番環境で実際に受信したデータ。ネットワークや取引所側の処理による遅延を含んだ形で届く。
- **レイテンシ（遅延）**：データの受信や注文の発注にかかる時間差。HFT では結果を左右する。
- **jitter**：遅延のばらつき。平均の遅延だけでなく、変動の幅まで再現すると、検証の現実味が増す。

## 3. 詳細解説

### なぜ補正が必要か

ヒストリカルデータは「市場で起きたこと」の記録であり、「bot の手元にいつ届いたか」の記録ではない。HFT のようにミリ秒単位の差が損益を分ける領域では、届くまでの遅延を無視したバックテストは、実稼働では再現できない有利な条件でモデルを評価してしまう。自己改善ループのように、バックテストの結果をもとに自動で改善を繰り返す仕組みでは、このずれがそのまま誤った改善の方向づけになる。

### 補正の手順

1. bot を実際に動かす環境（EC2 インスタンスなど）で、1〜2日分のリアルタイムデータを保存する。期間は、購入できるヒストリカルデータと重なるようにする。
2. 保存したリアルタイムデータと、同じ期間のヒストリカルデータを比較する。
3. 受信などで生じるレイテンシの差を、パラメータとして算出する。
4. 算出したパラメータをヒストリカルデータに適用する。
5. 補正したデータを使ってバックテストする。

### 対象とする遅延パラメータ

| パラメータ | 内容 |
| --- | --- |
| マーケットデータの受信遅延 | ヒストリカルデータと、bot が実際に受信するデータとの時刻差 |
| 発注遅延 | 注文を発注したときに生じる遅延 |
| イベント受信までの遅延 | 発注時刻から、発注したことを示すイベントを手元で受信するまでの遅延 |

マーケットデータの遅延だけでなく、注文まわりの遅延もパラメータとして定量化し、バックテストエンジンに組み込むことが要点である。

### jitter の反映

より高度な方法として、単純な遅延だけでなく jitter（遅延のばらつき）もパラメータとしてバックテストに反映させる。遅延が一定でない現実を再現することで、遅延の変動に強いシステムを作れる。

## 4. 仕組み・構造

補正の流れを図にすると、次のとおりである。

```mermaid
flowchart LR
    A["実機で1〜2日分の<br/>リアルタイムデータを保存"] --> B["同じ期間の<br/>ヒストリカルデータと比較"]
    B --> C["遅延をパラメータ化<br/>受信・発注・イベント受信・jitter"]
    C --> D["ヒストリカルデータに<br/>パラメータを適用"]
    D --> E["補正済みデータで<br/>バックテスト"]
```

## 5. メリット・デメリット

### メリット

- バックテストが実稼働の条件に近づき、モデルの評価が現実的になる。
- 遅延の種類ごとにパラメータ化するため、どの遅延が結果に効いているかを見分けられる。
- jitter まで含めると、遅延の変動に対する弱さも検証できる。
- 自己改善ループと組み合わせると、検証の土台が固まり、自動改善の方向がぶれにくくなる。

### デメリット

- 実測用のリアルタイムデータを、本番と同じ環境で収集する手間と期間がかかる。
- 遅延パラメータは環境や時期で変わりうるため、古い実測に基づく補正は陳腐化する。
- 補正できるのは定量化できる遅延に限られ、滑り（価格のずれ）など他の現実との差は別途扱う必要がある。

## 6. 活用例

- **HFT bot のバックテスト（出典の事例）**：bot を動かす EC2 インスタンス上で1〜2日分のリアルタイムデータを保存し、Tardis / Databento のヒストリカルデータと比較して遅延パラメータを算出する。補正したデータでのバックテストを、自己改善ループの仮説検証に使う。
