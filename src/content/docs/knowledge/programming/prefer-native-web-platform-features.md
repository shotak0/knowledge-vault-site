# Web プラットフォーム標準機能を優先する

## 1. 概要

Web の実装では、JavaScript で作り直す前に、ブラウザ標準の機能で済まないかを確認する。GoogleChrome/modern-web-guidance の考え方から、「エージェント（と人間）は古いパターンに寄りがちである」という前提と、標準機能を安全に採用するための枠組みを抽出した。

## 2. 基本概念

- **レガシーパターンへの回帰**：学習データや慣習に大量の古いコードが含まれるため、生成されるコードは既定で古い解法に寄る。存在を知っている API でも、本番品質の実装パターンは不足しがちである。
- **Baseline**：機能のブラウザ対応状況を示すプロジェクト。採用可否は「今の対応状況」で判断する。
- **プログレッシブ・エンハンスメント**：基本を全環境で成立させ、対応環境で強化を上乗せする方針。
- **揮発性機能（volatile features）**：単一エンジンで出荷されて間もない、または安定化途中の機能。明示の同意なしに採用しない。

## 3. 詳細解説

標準機能で置き換えられる代表例（modern-web-guidance のカタログ分野から）は次のとおりである。

- **ダイアログとポップオーバー**：`<dialog>`、Popover API。フォーカス管理や Esc での閉鎖など、アクセシビリティの多くをプラットフォームが担う。自前の div と JS で作り直すと、その分を自分で背負うことになる。
- **アンカー位置指定（anchor positioning）**：ツールチップやメニューの位置決めを CSS で宣言できる。
- **フォーム**：`:user-invalid`（操作後にだけ無効を示す）、field-sizing（内容に合わせた自動サイズ）など、検証表示の作法が標準化されている。
- **レイアウト**：コンテナクエリ、subgrid、:has()、cascade layers。画面幅だけでなく、要素自身の幅に応じた組み方ができる。
- **色**：oklch 等のモダン色空間、color-mix()、light-dark()。知覚的に均一な色の操作や、テーマ分岐が宣言的に書ける。
- **動きと遷移**：View Transitions（画面遷移のなめらかさ）、scroll-driven animations、@starting-style（現れる瞬間の初期状態）。アニメーションの判断基準（[アニメーションと質感の判断基準](../design/animation-and-feel-decisions.md)）と組み合わせて使う。
- **性能**：投機的プリロード、INP の診断、scheduler.yield によるタスク分割。
- **ブラウザ内蔵 AI**：端末上の翻訳・要約・言語検出 API。サーバーに送らずに済む処理がある。

安全な採用の枠組みは次のとおりである。(1) 純粋に付加的な強化（古いブラウザで無視されてよいもの）と、重要な振る舞い（ダイアログ制御など）を区別する。(2) 重要な振る舞いにだけ、50行未満の軽い個別フォールバックか、条件付きで読み込むポリフィルを用意する。重いサードパーティバンドルは避ける。(3) Baseline の互換性データを参照して判断する。(4) Origin Trial や揮発性機能は、開発者の明示同意をゲートにする。(5) 機能ごとの落とし穴（例：fetchLater() のペイロード上限）を文書で確認する。

また、コードベースを走査してモダン化できるレガシーパターンを探す legacy-scan のような点検も有効である。

## 4. 仕組み・構造

判断の流れは次のようになる。

1. やりたいことに対して、標準機能があるか探す（ガイドや Baseline を引く）。
2. あれば、その機能が「付加的強化」か「重要振る舞い」かを分ける。
3. 重要振る舞いなら、軽いフォールバックを用意する。付加的なら無視される前提で入れる。
4. 揮発性機能は、明示の判断がある場合だけ使う。
5. 標準機能がない場合に限り、JS で実装する。

## 5. メリット・デメリット

メリットは、性能とアクセシビリティがプラットフォームから付いてくること、依存ライブラリと保守対象が減ること、ブラウザの進化に合わせて実装が（多くは自動で）良くなることである。

デメリットは、機能ごとの対応状況と落とし穴の確認が都度要ること、新しい機能ほど情報が少なく挙動の差異に当たることである。採用判断は時点依存であり、恒常的な正解ではない。

## 6. 活用例

- モーダルを自前実装する前に `<dialog>` と Popover API を検討する。
- ツールチップの位置計算を JS で書く前に、アンカー位置指定を検討する。
- ダーク／ライトの分岐をクラスで管理する前に、light-dark() と color-scheme を検討する。
- 既存コードベースの点検で、置き換え可能なレガシーパターンを洗い出す。
