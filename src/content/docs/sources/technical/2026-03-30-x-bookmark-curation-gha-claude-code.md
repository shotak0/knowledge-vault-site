# X.comブックマークをGitHub Actions × Claude Codeで自動キュレーションする

## 1. 要約

X.com のブックマークが「後で読む」から「永遠に読まない」に変わってしまう問題への対処として、X API v2、GitHub Actions、Claude Code を組み合わせ、ブックマークを毎日自動で分類・要約して Markdown ダイジェストとして蓄積する仕組みを紹介した技術記事である。

出発点は、週100件を超えるペースで増えるブックマークを手動で週次レビューしようとして3週間で挫折した経験である。著者が必要だったのは「読む」ことではなく「分類して優先度をつける」ことであり、それなら AI に任せられると考えた、というのが仕組みの発想である。

処理は、X API v2 の Bookmarks エンドポイントから前回以降の新規ブックマークだけを取得し、Claude Code の SKILL がカテゴリ分類、1行要約、優先度付けを行い、Markdown ダイジェストを生成して Git リポジトリにコミットする、という流れである。蓄積先のリポジトリは Obsidian などと組み合わせる想定になっている。

実装の中心的な苦労は、OAuth2 のリフレッシュトークンの扱いである。X API のリフレッシュトークンは使い捨て（ローテーション方式）で、リフレッシュすると古いトークンが無効になる。GitHub Actions の並列実行で複数のジョブが同じトークンでリフレッシュすると競合が起きるため、状態ファイルによるロックで対処し、新しいトークンは PAT を使って GitHub Secrets に自動で書き戻している。

運用の結果、「後で読む」が「週次レビューの素材」に変わり、重要なブックマークを見逃さなくなった。分類の精度は SKILL のプロンプトを4回調整して安定し、「ブログネタ候補」のフラグが付いたブックマークから実際に2本の記事が生まれた。一方で、Bookmarks API は有料プラン必須、取得は最大800件まで、Claude API のコストが1回あたり約0.02〜0.05ドルといった制約も、実測として記録されている。

## 2. 重要なポイント

- 問題の捉え直しが仕組みの出発点である。ブックマークの山に必要だったのは「読む」ことではなく「分類して優先度をつける」ことで、それなら AI に任せられる、という判断である。
- 構成は、取得（X API v2、差分のみ）、分類（Claude Code の SKILL）、出力（Markdown ダイジェストをリポジトリにコミット）の3段である。毎日の定時実行は GitHub Actions の cron で行う。
- Bookmarks エンドポイントは無料プランでは使えず、最低でも Basic プラン以上が必要である。記事中の参考価格では Basic が月額200ドルとされている一方、運用してわかった制約の節では、従量課金（Pay-Per-Use、1リソースあたり0.005ドルから）で少量利用なら低コスト、と記されている。
- 認証は OAuth 2.0 の Authorization Code Flow with PKCE である。必要なスコープは bookmark.read、tweet.read、users.read、そしてリフレッシュトークンを得るための offline.access で、offline.access を忘れるとアクセストークンの有効期限（2時間）後に自動更新できなくなる。
- レート制限は180リクエスト／15分／ユーザーで、1リクエストで最大100件取得できるため、日次実行なら十分だとされている。
- 重複排除は状態ファイル方式である。Bookmarks API は実測上、ブックマーク追加日時の降順で返すため、先頭のブックマーク ID を記録しておけば、前回以降の新規分だけを差分取得できる。
- 分類の出力は構造化されている。カテゴリ（AI-Tools、Dev、Productivity、Business、News、Other の6つ）、コンテンツ化の可能性（blog、x-post、note、dev-idea、none）、1行要約、なぜブックマークしたかの推測、優先度（high、medium、low）を、各ブックマークについて出す。
- リフレッシュトークンはローテーション方式で、リフレッシュすると新しいトークンが発行され、古いトークンは無効になる。並列ジョブが同じトークンでリフレッシュすると、後発のジョブが失敗する競合が実際に起きた。
- 競合への対処は、状態ファイルによるロック（5分のタイムアウト付き）である。ロックが取れなければその実行ではリフレッシュしない。
- リフレッシュで得た新しいトークンは、GitHub Secrets に書き戻す必要がある。その更新には PAT が必要で、暗号化はリポジトリの公開鍵と libsodium の Sealed Box で行う。PAT の権限は、対象リポジトリの Secrets の読み書きのみに絞ることが強く求められている。
- 運用で分かった制約として、取得できるのは最大800件まで（大量に貯める人は取りこぼすため、取得頻度を上げる対処）、リフレッシュトークンは長期間未使用だと失効する（最低週1回の実行を維持）、Claude API のコストはダイジェスト1回あたり約0.02〜0.05ドル（月1〜2ドル程度で実用的）が挙げられている。
- 分類精度は、SKILL のプロンプトを4回調整する反復で安定した。初回はカテゴリの粒度が荒かった。SKILL として分類ロジックを定義しておくことで、運用中の調整が容易になる、とまとめられている。
- 改善したいこととして、Discord へのダイジェスト投稿とモバイル確認、Discord 上からのインタラクティブな指示、複数アカウント対応が挙げられている。

## 3. 詳細解説

### 3.1 背景：ブックマークが溜まるだけ問題

著者の X.com ブックマークは、週100件を超えるペースで増えていた。AI ツールの新機能、気になる OSS の紹介、技術的な Tips を「あとで読もう」とブックマークするものの、振り返る習慣がないまま埋もれていく。手動の週次レビューは、100件を1つずつ開いて読む作業が退屈で、3週間で挫折した。

ここでの著者の判断は、「必要だったのは『読む』のではなく『分類して優先度をつける』こと」というものである。全部を読む作業は人にも重いが、分類と優先度付けなら AI に任せられる。この捉え直しが、仕組み全体の出発点になっている。

### 3.2 全体アーキテクチャ

処理の流れは3段である。

1. **取得**：X API v2 でブックマークを取得する（前回以降の新規のみ）。
2. **分類**：Claude Code が各ブックマークをカテゴリ分類し、1行要約を付ける。
3. **出力**：Markdown ダイジェストを生成し、リポジトリにコミットする。

実行基盤は GitHub Actions で、毎日定時（記事のワークフロー例では 07:30 JST）に動き、手動実行も可能である。蓄積先は Git リポジトリで、Obsidian などと組み合わせる想定である。

### 3.3 X API v2 Bookmarks エンドポイント

前提として、Bookmarks エンドポイントは無料（Free）プランでは利用できず、最低でも Basic プラン以上が必要である。記事の料金表（参考）では、Free は月額0ドルで利用不可、Basic は月額200ドル、Pro は月額5,000ドルとされている。ただし、運用の節では Pay-Per-Use 制（1リソースあたり0.005ドルから）で、従量課金なので少量利用なら低コスト、とも記されている。

エンドポイントは `GET /2/users/:id/bookmarks` で、パラメータは max_results（1〜100、既定100）、pagination_token、tweet.fields、expansions である。レート制限は180リクエスト／15分／ユーザーで、1リクエスト最大100件のため、日次実行なら十分だとされている。

必要な OAuth スコープは、bookmark.read（ブックマーク読み取り）、tweet.read（ツイート情報取得）、users.read（ユーザー情報取得）、offline.access（リフレッシュトークン取得）の4つである。offline.access を忘れると、アクセストークンの有効期限（2時間）が切れた後に自動更新できなくなる点が、重要として強調されている。

### 3.4 OAuth2 PKCE 認証の実装

X API v2 の OAuth 2.0 は、Authorization Code Flow with PKCE を採用している。PKCE は認可コードの横取り攻撃を防ぐ仕組みで、もともと RFC 7636 でパブリッククライアント向けに設計されたが、OAuth 2.1 ではサーバーサイドを含む全クライアントで推奨されており、X API も両方をサポートしている。

初回認証の流れは、code_verifier（ランダム文字列）の生成、それを SHA256 ハッシュして Base64URL 化した code_challenge の作成、認可 URL をブラウザで開いてユーザーが承認、リダイレクト URL から認可コードを取得、認可コードと code_verifier でトークンエンドポイントに POST し、access_token と refresh_token を得る、という手順である。refresh_token は後で使うため、安全に保管する。

初回だけが手動で、以降はリフレッシュトークンによる自動更新になる。

### 3.5 GitHub Actions ワークフロー

ワークフローは、毎日定時の schedule と手動実行（workflow_dispatch）で動き、制限時間は10分、リポジトリへの書き込み権限（contents: write）を持つ。ステップは、チェックアウト、Python 3.12 のセットアップ、依存関係（requests）のインストール、ブックマーク取得スクリプトの実行、Claude Code（anthropics/claude-code-action）による分類、結果のコミットと push、という順である。

Secrets には、X_CLIENT_ID、X_CLIENT_SECRET、X_REFRESH_TOKEN、GH_PAT_FOR_SECRETS（Secrets 更新用の PAT）、ANTHROPIC_API_KEY の5つを設定する。

### 3.6 ブックマーク取得スクリプトと重複排除

取得スクリプトの核は、refresh_token で access_token を再取得する処理、ブックマーク一覧をページネーションしながら取得する処理、前回以降の新規分だけを抽出する処理である。

重複排除の仕組みは、状態ファイル（state.json）に最新のブックマーク ID と前回実行日時、件数を記録する方式である。Bookmarks API は、公式ドキュメントに明記はないものの、実測上はブックマーク追加日時の降順で返すことが開発者コミュニティでも多数確認されている。そのため、一覧の先頭の ID を記録しておけば、次回はその ID に行き当たるまでの分だけが新規分として差分取得できる。

### 3.7 Claude Code SKILL による AI 分類

分類ロジックは、Claude Code の SKILL として定義されている。入力はツイート本文とメトリクス（いいね数、RT 数、ブックマーク数）で、出力は次の構造である。

- **category**：AI-Tools、Dev、Productivity、Business、News、Other の6分類。AI-Tools は AI ツール・サービス関連、Dev は開発技術・ライブラリ、Productivity は生産性・ワークフロー、Business はビジネス・マーケティング、News はニュース・速報である。
- **content_potential**：blog、x-post、note、dev-idea、none の中から、そのブックマークがどんなコンテンツの種になるか。
- **summary**：1行要約。
- **key_insight**：なぜブックマークしたかの推測。
- **priority**：high、medium、low の優先度。

生成されるダイジェストは、日付と新規件数を冒頭に置き、カテゴリ別に件数つきで並べ、各項目にタイトルとメトリクス（いいね数、ブックマーク数）と「開発ガイド記事のネタ候補」のような使い道の注記を付け、末尾に注目のピックアップと統計（合計、カテゴリ別件数、コンテンツ候補の内訳）を置く形式である。

### 3.8 OAuth2 トークンリフレッシュの競合問題

著者が「一番ハマったポイント」とするのが、リフレッシュトークンの競合である。X API の OAuth2 リフレッシュトークンは使い捨て（ローテーション方式）で、リフレッシュすると新しいトークンが発行され、古いトークンは無効になる。

GitHub Actions では複数のジョブが並列実行される場合がある。ジョブ A が refresh_token_v1 でリフレッシュして v2 を得たあと、ジョブ B が同じ v1 でリフレッシュしようとすると、v1 はすでに無効なため失敗する。

解決策は、状態ファイルによるロックである。ロックファイルにロック取得時刻とジョブ ID を書き、5分（300秒）のタイムアウトを設ける。ロックが有効な間はリフレッシュを行わず、タイムアウトを過ぎた古いロックは無視する。

あわせて、リフレッシュで得た新しいトークンを GitHub Secrets に書き戻す処理が必要になる。これには PAT が必要で、手順は、リポジトリの公開鍵を取得し、libsodium の Sealed Box で秘密情報を暗号化し、Secrets の更新 API に送る、というものである。著者は、PAT の権限は対象リポジトリの Secrets の読み書きのみに絞ることを強く求めている。

### 3.9 運用してわかったこと

うまくいったことは3つある。「後で読む」が「週次レビュー素材」に変わり、ダイジェストを週末にざっと見るだけで重要なブックマークを見逃さなくなったこと。分類精度が、SKILL のプロンプト調整4回の反復で安定したこと（初回はカテゴリの粒度が荒かった）。コンテンツのネタ発見の効率が上がり、「ブログネタ候補」のフラグが付いたブックマークから実際に2本の記事化ができたこと、である。

制約と注意点は、料金の節でも触れたとおり、Bookmarks API は有料プラン必須（従量課金で少量利用なら低コスト）、取得は最大800件まで（大量ブックマーク派は取りこぼすため、取得頻度を週2〜3回に上げる対処）、リフレッシュトークンは長期間未使用だと失効する（最低週1回の実行を維持）、Claude API のコストは1回あたり約0.02〜0.05ドル（月1〜2ドル程度で実用的）、である。

改善したいこととして、Discord 連携（ダイジェスト投稿とモバイル確認）、Discord 上からのインタラクティブな指示（「このブックマークをブログリサーチに追加して」など）、複数アカウント対応が挙げられている。

## 4. 重要な用語

- **キュレーション**：集まった情報を、分類や優先度付けによって、後から見返して使える形に整えること。この記事では、ブックマークを「読む」のではなく「分類して優先度をつける」という捉え直しの中核にある言葉である。
- **X API v2 Bookmarks エンドポイント**：認証したユーザーのブックマーク一覧を取得する X API のエンドポイント。有料プランでのみ利用できる。
- **PKCE**：認可コードの横取り攻撃を防ぐための OAuth 2.0 の拡張（RFC 7636）。code_verifier と code_challenge の組で認可コードの交換を保護する。
- **offline.access**：リフレッシュトークンを取得するために必要な OAuth スコープ。これがないと、アクセストークンの失効後に自動更新できない。
- **リフレッシュトークンのローテーション**：リフレッシュのたびに新しいリフレッシュトークンが発行され、古いものが無効になる方式。使い捨てであるため、並列実行や保存漏れに弱い。
- **SKILL（Claude Code）**：Claude Code に分類ロジックのような定型の処理手順を定義しておく仕組み。この記事では、ブックマーク分類の入出力形式とカテゴリ定義を SKILL として定義している。
- **GitHub Secrets の書き戻し**：ワークフロー実行中に得た新しい秘密情報（ここでは新しいリフレッシュトークン）を、PAT と公開鍵暗号化を使って GitHub Secrets に保存し直す処理。
- **差分取得（状態ファイル方式）**：前回処理した最後の項目の ID を状態ファイルに記録し、次回はそこまでの新規分だけを取得・処理する方式。

## 7. AIによる考察

※この節は AI による考察であり、元記事の内容ではない。

この記事のいちばんの要点は、技術の組み合わせよりも、「ブックマーク問題は読書の問題ではなく、トリアージ（優先度付け）の問題である」という捉え直しにあるように思う。週次レビューが3週間で挫折したという失敗の記録が、その根拠として効いている。全部を読む設計は、量が増えた時点で破綻する。分類と優先度付けを先に機械へ渡し、人はダイジェストの形になったものだけを見る、という分担は、量に耐える設計である。

分類の出力に content_potential（そのブックマークがどんなコンテンツの種になるか）を含めている点も示唆的である。単なる分類ではなく「使い道」まで推定させることで、ダイジェストがそのまま次の行動の候補リストになる。実際に2本の記事が生まれたという結果は、その設計の効果として記録されている。

また、リフレッシュトークンの競合は、API の仕様（ローテーション方式）と実行基盤の性質（CI の並列実行）の組み合わせで初めて現れる種類の問題で、個別のドキュメントだけでは予見しにくい。著者が「一番ハマったポイント」として手順とコードとともに残していることは、この記事の再利用価値を高めている。

なお、この記事の仕組みは X のブックマーク専用だが、「入口で自動分類し、ダイジェストにして週次で見返す」という形そのものは、他のストック（RSS、後で読むサービス、リンク集）にも移せる一般形だと考えられる。Readwise のライブラリ構成や Karakeep のような製品が扱っているのも、同じ問題の別の側面である。
