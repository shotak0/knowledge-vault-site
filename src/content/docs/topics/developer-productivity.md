# 開発者生産性

## 1. 概要

このテーマでは、開発者の生産性を、コードレビューと検証という角度からまとめる。中心となる問いは、エージェントが大量のコードを生成する時代に、レビューと検証の質をどう保つか、である。

現時点では、情報源は1件のみである。Addy Osmani による X の長文記事「Critical thinking when agents do the work」（2026-11-03）と、そこから抽出した Knowledge「エージェント作業における検証の習慣」をもとにまとめたものである。情報源が1件のみであるため、複数の情報源の比較はまだできない。情報が追加されたら、このテーマも更新する。

## 2. 基本概念

- **コードレビュー**：他人のコード変更を読み、問題や改善点を確認する作業。品質と知識の共有の両方の役割がある。
- **プルリクエスト**：コードの変更を提案し、他の人がレビューしてから取り込むための仕組み。変更の内容と意図がまとめて確認できる。
- **検証**：出力が正しいか、意図に沿っているか、副作用がないかを確かめる行為。テストの通過、目視の確認、ログや実行結果の確認などが含まれる。
- **ゴム印化（rubber stamping）**：レビューが、内容の確認ではなく、形式的な承認になってしまう状態。量が多すぎると、人は細部を読まずに承認してしまう。
- **検証の手段**：エージェントに渡す、確認のための仕組み。エンドツーエンドのテスト、プロパティテスト、実際のアプリ操作などが含まれる。
- **オーケストレーションの負担（orchestration tax）**：エージェントが生成した量と、自分が責任を持てる量の差。生成量が責任の範囲を超えると、レビューの負担が増える。

## 3. 技術・知識の体系

開発者生産性とレビュー・検証の関係は、次の三つの層で整理できる。

1. **生成の層**：エージェントがコードを生成する。生成は安く、速い。大量のコードが短時間で出てくる。
2. **検証の層**：生成されたコードが正しいかを確かめる。「検証済み」の定義を事前に決め、検証の手段をエージェントに渡し、実行結果という証拠を確認する。詳しくは [エージェント作業における検証の習慣](../knowledge/ai/verification-for-agent-work.md) を参照すること。
3. **レビューの層**：変更を人が承認する。変更の意図と、エージェントが下した決定・前提を確認する。量が多すぎると、レビューはゴム印になりやすい。

生産性を上げるには、生成の層だけでなく、検証とレビューの層を整える必要がある。生成だけが速くなっても、検証とレビューが追いつかなければ、承認できない変更が積み上がるだけである。

## 4. 重要な論点

- **レビューは「読むこと」から「判断すること」へ移る**。エージェントがコードを書く量が増えるほど、人は一行ずつ読むのではなく、変更の意図と、エージェントが下した決定・前提を確認するようになる。
- **量が増えるとレビューはゴム印になりやすい**。600行のプルリクエストでは、人は細部を読まずに承認してしまう。変数名が妥当に見え、テストが通っていれば、承認してしまいがちである。しかし、変更の途中には、取引の境界での順序の変更や、想定していなかった端の場合の既定値の変更など、見落としやすい変更が紛れていることがある。
- **緑のチェックは一つの性質しか示さない**。テストが通ったことは、そのテストで確認した範囲が通ったことであり、すべてが正しいことの証明ではない。テストが、機能と同じ間違いを含んで作られていれば、間違ったまま通ってしまう。
- **生成量と責任の範囲の差が負担になる**。生成された量と、自分の名前を付けられる量の差が、オーケストレーションの負担である。仕上がった作業が、確認できる速さより速く積み上がるなら、別のセッションを増やす前に、確認の仕組みを締めるか、速度を落とす必要がある。自分の名前を付けられる量を超えて生み出しているときは、レビューをしているのではなく、うまくいくことを願っているだけである。
- **検証の深さは場面で変える**。すべてを深く検証する必要はない。「チェックが見逃すものを言えないなら、簡単な承認ではなく、きちんとしたレビューを頼む」という基準がある。
