# クラウドインフラ

## 1. 概要

このテーマでは、クラウドインフラの障害への備えを、横断的にまとめる。中心となる問いは、あるリージョンでシステムを動かしていても、別のリージョンへの依存が残る場合に、障害のときに何が起きるか、である。

現時点では、情報源は1件のみである。yama3133 による Qiita の記事「東京リージョンで使っていてもバージニア北部に依存しているもの」（2026-11-06）と、そこから抽出した Knowledge 2件をもとにまとめたものである。情報源が1件のみであるため、複数の情報源の比較はまだできない。情報が追加されたら、このテーマも更新する。

更新履歴：2026-11-10 に、Qiita の記事と Knowledge 2件をもとに初版を作成した。

## 2. 基本概念

- **リージョン**：AWS のサービスを提供する地理的な単位。東京リージョンは `ap-northeast-1`、バージニア北部リージョンは `us-east-1` である。
- **コントロールプレーン**：サービスの管理機能。設定の作成・変更・削除などを行う側である。
- **データプレーン**：実際に処理を行う側。名前解決、コンテンツの配信、認証の確認など、ふだんの利用の処理を行う。
- **グローバルサービス**：リージョンをまたいで共通に使われるサービス。IAM、Route 53、CloudFront などがこれにあたる。管理機能は us-east-1 に集まっているものが多い。
- **静的安定性（static stability）**：依存先の管理機能が止まっても、何も変更せずに動き続けられる性質。
- **フェイルオーバー**：障害が起きたときに、待機側の構成へ切り替えること。
- **障害分離境界（fault isolation boundary）**：障害の影響が広がらないように分ける境界。AWS公式ホワイトペーパー「AWS Fault Isolation Boundaries」で説明されている考え方である。

## 3. 技術・知識の体系

クラウドインフラの障害への備えは、次の三つの層で整理できる。

1. **分離の層**：コントロールプレーンとデータプレーンを分けて考える。管理機能が止まっても、処理を行う側が動き続けていれば、既存のサービスは動き続ける。詳しくは [コントロールプレーンとデータプレーンの分離](../knowledge/infrastructure/control-plane-and-data-plane-separation.md) を参照すること。
2. **備えの層**：静的安定性を保ち、復旧手順やフェイルオーバーの操作が、止まる可能性のある管理機能に依存していないかを確認する。詳しくは [静的安定性と障害時の備え](../knowledge/infrastructure/static-stability-and-outage-preparedness.md) を参照すること。
3. **確認の層**：ログや監視の置き場所を確認する。障害の最中に確認したい情報が、障害の影響を受ける場所に置かれていないかを確認する。CloudTrail を全リージョン対象の証跡にしておくことや、STS は東京のリージョナルエンドポイントを使うことなどが、これにあたる。

この三つの層は、別々のものではなくつながっている。分離の理解がなければ、備えの設計はできない。備えができていても、ログの置き場所を確認していなければ、障害の最中に状況が把握できない。だからこそ、三つの層をまとめて考える必要がある。

## 4. 重要な論点

- **「使っているリージョン」と「依存しているリージョン」は別物である**。東京リージョンを指定してリソースを作れば、東京で完結しているように見える。しかし、管理機能の置き場所や、ログの置き場所、グローバルサービスの仕組みまで含めて見ると、us-east-1 に依存している部分が残る。
- **障害の影響は「動き続けるもの」と「できなくなるもの」に分かれる**。稼働中の EC2 / Lambda / RDS、Route 53 の名前解決、CloudFront の配信、発行済み認証情報による認証は基本的に動き続ける。一方で、IAM の作成・変更、Route 53 レコードの変更、CloudFront の設定変更、Organizations の操作はできなくなる可能性がある。障害への備えは、この分かれ方を事前に整理することから始まる。
- **復旧手順そのものが依存を持っている**。障害の最中に設定を変更して復旧する手順は、その変更操作自体が止まっている管理機能に依存していると、使えない。復旧手順を作るときは、手順の一つひとつの操作が、どの管理機能に依存しているかを確認する必要がある。
- **確認できていないことは、確認できていないと記録する**。CloudFront 標準ログの CloudWatch Logs への送り先となるロググループのリージョンや、障害の最中にログがどう振る舞うかについては、情報源の記事内では確認できていないとされている。推測で補わず、確認できていないことはそのまま残しておく。
