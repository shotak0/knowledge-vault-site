## 2. 基本概念

- **JWT（JSON Web Token）**：JSON オブジェクトを署名付きの文字列として受け渡す形式。ヘッダー、ペイロード、署名の3部を Base64Url エンコードしてピリオドで連結する。
- **クレーム**：トークンに含まれる個々の情報。発行者（iss）、対象者（sub）、受信者（aud）、有効期限（exp）、有効開始時刻（nbf）、発行日時（iat）、一意な識別子（jti）という標準クレームがある。
- **署名**：内容が改ざんされていないことを検証する仕組み。再計算した署名との一致で完全性を確認する。
- **Base64Url**：URL に使えない文字を避けたエンコード方式。可逆な変換であり、暗号化ではない。
- **HS256**：HMAC + SHA-256 の署名方式。署名と検証に同じ秘密鍵を使う共通鍵方式である。
- **kid（Key ID）**：ヘッダーに任意で追加できる鍵の識別子。検証側が鍵を選ぶ手がかりになる。

## 3. 技術・知識の体系

現時点の体系は、JWT を中心に、次の2つの知識で構成される。

1. **JWT の構造とクレーム**：3部構成、Base64Url、署名による改ざん検出、標準クレームの読み方を整理する。JWT が担保するのは秘匿性ではなく完全性である、という区別が出発点になる。詳しくは [JWTの構造とクレーム](../knowledge/security/jwt-structure-and-claims.md) を参照すること。
2. **Go での生成と検証**：golang-jwt による生成の3ステップと、署名方式の確認を含む検証の流れを、実装パターンとして整理する。詳しくは [GoでのJWT生成と検証](../knowledge/security/jwt-generation-and-validation-in-go.md) を参照すること。

この2つは、「形式の理解（構造）→ 実装での落とし込み（生成と検証）」という流れになっている。その背後には、トークン形式の安全性は、形式そのものだけでなく、検証側の確認手順と鍵の管理で決まる、という考え方がある。

## 4. 重要な論点

- **エンコードと暗号化は違う**。JWT のペイロードは誰でも読める。読まれて困る情報を入れる設計は成り立たない。
- **検証は多段である**。署名の照合だけでなく、署名方式が想定どおりか、有効期限内か、発行者と宛先が正しいかを確認して初めて受け入れられる。
- **鍵の管理が信頼の境界になる**。共通鍵方式では、鍵を持つ主体はすべてトークンを発行できる。鍵の保管と共有範囲が、そのままセキュリティの水準を決める。
- **形式の理解だけでは運用は完結しない**。トークンの保存場所、失効の扱い、漏れた場合の対処といった運用面は、今回の情報源では扱われていない。今後の情報源で補うべき領域である。
