# 知識管理

## 1. 概要

このテーマでは、集めた情報（ブックマーク、後で読む文書、リンクのストック）を、どう捌いて、どう蓄積し、どう再利用するかを横断的にまとめる。中心となる問いは、保存の量が人の処理の量を超えたときに、ストックを「永遠に読まない山」にしないためにはどうするか、である。

2026-11-21 に、初版として3件の情報源をもとに作成した。amu_lab の Zenn 記事「X.comブックマークをGitHub Actions × Claude Codeで自動キュレーションする」（2026-03-30）は、X のブックマークを AI に自動で分類させ、ダイジェストとして蓄積する自作パイプラインの実践である。Readwise の公式ガイド「How to choose a Library configuration」は、後で読むストックを人が捌く処理の型（トリアージ型、ショートリスト型、クラシック型）を整理したものである。Karakeep の公式サイトは、保存した瞬間に AI がタグ付けと要約を行い、検索で再発見できるようにする製品の側の実装である。

3件は同じ問題の異なる側面を扱っている。入口で自動分類するか（Zenn 記事、Karakeep）、人が捌く処理の型をどうするか（Readwise）、蓄積したものをどう再発見するか（Karakeep の検索、Zenn 記事のダイジェスト）である。以下の §2〜§5 は、この3件をもとに統合したものである。

更新履歴：2026-11-21 に、情報源3件と Knowledge 3件をもとに初版を作成した。

## 2. 基本概念

- **ストック**：後で読む・使うために保存した情報の集まり。ブックマーク、読み物の保存、リンク集などを指す。
- **キュレーション**：集まった情報に分類と優先度を付けて、後から見返して使える形に整えること。
- **トリアージ**：入ってきたものを1件ずつ判断して行き先を決める処理の型。保存したものすべてに判断を通す前提である。
- **ショートリスト**：大きな山から優先度の高いものだけを引き上げた、小さな読みキュー。山と読みキューを分けることが要点である。
- **アンチライブラリ**：Readwise のガイドの言葉で、「いつか読むかもしれないもの全部」を抱える未読の山のこと。ショートリスト型では、この山の存在を認めたうえで設計する。
- **ダイジェスト**：分類結果をカテゴリ別にまとめた文書。人が実際に目を通す対象を、ストックそのものからダイジェストに移すことが、自動キュレーションの要点である。
- **差分取得**：前回処理した最後の項目を状態として記録し、次回は新規分だけを取得・処理する方式。
- **保存時の自動分類**：保存した瞬間に AI がタグ付けと要約を行う方式。整理という後工程そのものをなくす考え方である。
- **セマンティック検索**：語句の一致ではなく意味の近さで探す検索。再発見の手段の一つである。

## 3. 技術・知識の体系

このテーマの情報源は、ストックの流れを3つの段階で整理すると位置づけが明確になる。

1. **入口（集めて、仕分ける）**：ストックが入ってくる段階である。ここでの設計は、自動分類をどこまでやるかである。Zenn の記事は、毎日定時に新規分を取得し、AI がカテゴリ、1行要約、優先度、使い道を付ける。Karakeep は、保存した瞬間に AI がタグ付けと要約を行い、URL パターンによる自動振り分けのルールや、RSS の自動取り込みも備える。詳しくは [ブックマークの自動キュレーション：分類と優先度付けをAIに任せる仕組み](../knowledge/general/bookmark-curation-with-ai-classification.md) を参照すること。
2. **処理（型を選んで捌く）**：入ったものを人がどう読み進めるかの段階である。Readwise の3つの型（トリアージ型、ショートリスト型、クラシック型）は、この段階の設計の選択肢である。全件に判断を通すか、山を認めて選別だけを小さく保つか、仕分け自体を最小にするか、が違いである。詳しくは [読み物ストックの処理ワークフロー：トリアージ型・ショートリスト型・クラシック型](../knowledge/general/read-it-later-library-workflows.md) を参照すること。
3. **蓄積と再発見（残して、引き出せるようにする）**：捌いたものをどう残し、あとからどう引き出すかの段階である。Zenn の記事は Markdown ダイジェストを Git リポジトリに蓄積し、週次レビューの素材にする。Karakeep は、ページ全体のアーカイブでリンク切れに備え、全文検索、セマンティック検索、OCR 検索で再発見できるようにする。

この3段階を支える土台として、自動化の維持の問題がある。自動で回す仕組みは、認証トークンの管理のような、表の機能とは別の維持コストを持つ。Zenn の記事が記録した OAuth リフレッシュトークンのローテーション競合は、その代表例である。詳しくは [OAuthリフレッシュトークンのローテーション競合とSecretsへの書き戻し](../knowledge/security/oauth-refresh-token-rotation-in-ci.md) を参照すること。

## 4. 重要な論点

- **問題は「読む」ことではなく「分類して優先度をつける」ことである**。保存のコストと読むコストの非対称により、全部を読む前提の設計は量の増加で破綻する。分類と優先度付けを先に機械へ渡し、人はダイジェストや読みキューだけを見る分担が、量に耐える。
- **分類には「使い道」まで含めると、ストックが行動の候補になる**。カテゴリと要約だけの分類は整理された一覧で終わるが、そのストックが何の種になるか（記事化、アイデア化など）まで推定させると、ダイジェストは次の行動の候補リストになる。Zenn の記事では、フラグの付いたブックマークから実際に2本の記事が生まれている。
- **全件判断は、量が判断量を超えた時点で破綻する**。トリアージ型は状態が明確だが、受信箱自体が山になりうる。ショートリスト型は山を認める代わりに破綻しない。処理の型は、自分の保存量と判断量の関係で選ぶものである。
- **処理の型は、切り替えられること自体が価値になる**。Readwise では型をいつでも変更でき、文書は自動で移される。整理法の選択は固定化しがちだが、移行コストが低いことで「試して見つける」が可能になる。
- **優先の区別は、構造でも目印でも実装できる**。置き場所で分ける方法と、タグで目印を付けて横断的に拾う方法がある。どちらを選ぶかは、状態の明確さと柔軟さの交換である。
- **自動化には、見えない維持コストが伴う**。ローテーション方式のリフレッシュトークンのように、自動実行を続けるためだけの仕組み（ロック、Secrets への書き戻し、最小権限の PAT）が要る場合がある。自動化の設計では、この維持の層も含めて見積もる必要がある。

## 5. 情報源ごとの比較

3件の情報源は、同じ問題への3つの異なるアプローチとして対比できる。

| 情報源 | アプローチ | 主に担う段階 | 人の役割 |
| --- | --- | --- | --- |
| amu_lab の Zenn 記事 | 自作パイプライン（API 取得＋AI 分類＋ダイジェスト蓄積） | 入口、蓄積 | ダイジェストを週次で見て拾う |
| Readwise の公式ガイド | 処理の型の選択肢の提示（3つのライブラリ構成） | 処理 | 型を選び、型に沿って捌く |
| Karakeep 公式サイト | 製品（保存時の AI 分類、検索、自動化ルール） | 入口、再発見 | 保存し、検索で引き出す |

共通しているのは、どの情報源も「保存した人の手で全部を捌く」ことを前提にしていない点である。違いは、捌く作業をどこへ移すかで、Zenn の記事は自作の自動分類へ、Readwise は処理の型の設計へ、Karakeep は製品の AI と検索へ、それぞれ移している。

また、Zenn の記事と Karakeep は、同じ「自動分類」を、定期実行（貯まったものを捌く）と保存時（貯まる前に捌く）という異なるタイミングで実装している。分類のタイミングは、自動キュレーションの設計の主要な選択肢である。

## 8. 今後の課題・考察

- **分類体系の統制**：AI の自動分類は、タグやカテゴリの語彙が AI 任せになることを意味する。自分の分類体系（固定のカテゴリ、タグの表記ルール）を持つ場合、その体系に AI の出力をどう寄せるかが課題である。Karakeep の公式サイトの範囲では、タグ語彙そのものの統制の仕組みは読み取れなかった。
- **入口の制約の確認**：自動キュレーションは入口の API の制約に左右される（Zenn の記事では有料プラン必須、取得上限800件など）。入口ごとに制約と料金を確認することが、設計の前提になる。
- **ダイジェストの先の知識化**：ダイジェストやストックは、見返して拾うところまでが情報源の扱う範囲である。拾ったものを再利用可能な知識にどう変えるかは、このテーマの次の段階の問いである。
- **自動化の維持の見積もり**：自動で回す仕組みには、トークン管理のような維持の層がある。仕組みを作る際に、維持コストまで含めて続く形かどうかを見積もることが課題である。
